# Pawport

A calm, private pet health passport built with Next.js App Router, TypeScript, Tailwind CSS, Supabase Auth/Postgres, and Vercel. The thin slice supports email signup and confirmation, one household and one pet per account, vaccination entry, and temporary read-only share URLs with locally generated QR codes and revocation.

## Run locally

Requires Node.js 22+ and npm.

```sh
npm ci
cp .env.example .env.local
npm run dev
```

Without Supabase environment variables, `/` displays a **clearly labeled, read-only sample dashboard**. Sample actions open an explanation and link to signup; they never pretend to persist data. Configure Supabase for the real workflow.

## Connect Supabase

1. Create a Supabase project. Apply `supabase/migrations/202609110001_passport.sql` using the SQL editor or `supabase db push` after linking the project. This is an initial migration for a new database.
2. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` from the project API settings. A legacy anon key also works. **No service-role key is used by the app.**
3. Set `NEXT_PUBLIC_APP_URL` to `http://localhost:3000` locally and the exact canonical HTTPS app origin in production. This trusted configuration generates auth and share URLs; request Host headers are never trusted for them.
4. Enable Email authentication and email confirmation. Set Auth Site URL to the app origin and allow `http://localhost:3000/auth/confirm` and your production `/auth/confirm` URL in Auth Redirect URLs.
5. For confirmation links that work across browsers, customize the Confirm signup email template link to:
   ```html
   <a href="{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=email"
     >Confirm your email</a
   >
   ```
   The callback also supports the default PKCE `code` flow in the browser that initiated signup.
6. Set the Supabase minimum password length to 12. Configure production SMTP and Supabase Auth rate limits before inviting users. Use a separate Supabase project for previews and tests.

Then sign up, confirm the email, create a household, add a pet, add a vaccination, and create a share pass. Open the link in a signed-out browser, then revoke it and reload to verify access ends.

## Deploy to Vercel

Import this directory as a Next.js project. Use Node.js 22+, install `npm ci`, build `npm run build`, and the default Next.js output. Add all three `.env.example` variables in the Vercel environment. Set the production app URL to the final HTTPS domain, apply the database migration, update Supabase redirect settings, and redeploy after changing public environment variables. No Vercel-specific server or filesystem persistence is needed.

## Security model

- Each household has exactly one immutable owner. Unique constraints enforce one household per account and one pet per household. Invites, collaborators, editing, uploads, billing, and medical interpretation are outside this slice.
- RLS protects every table. The app uses the caller’s cookie-authenticated Supabase client. Every mutation independently validates the user with `getUser()` and validates input with Zod. Database constraints defend direct API writes too.
- Anonymous roles have no table access. Authenticated roles have only the table operations needed by the MVP. They cannot reassign ownership, modify records, insert share tokens, extend expiry, or read token hashes.
- Passes use 256-bit random tokens generated by Postgres; only SHA-256 hashes are stored. Tokens are displayed once. Durations are allowlisted (1 hour, 24 hours, 7 days), with a database constraint and a race-safe cap of five active passes per pet.
- The three narrowly scoped `SECURITY DEFINER` functions have an empty search path, explicit authorization (for mutations), and explicit execution grants. The anonymous read function checks token format, digest, expiry, and revocation and returns a fixed field allowlist. It does not expose internal IDs, owner data, household data, or microchips.
- Shared responses are dynamic and uncached, with no-referrer and noindex headers. QR generation is local; there is no external QR or analytics service. Keep token paths out of external analytics, error capture, and long-lived access logs when configuring hosting observability. A pass is a bearer credential; viewers can retain information already seen.
- Sessions refresh through Next.js Proxy; authorization remains in actions and RLS. Shared reads use an isolated anonymous client. Same-origin Server Action protections are retained.
- Dates are ISO date-only values, validated for calendar correctness and chronology. “Recorded” describes an entry, not vaccination verification or clinical immunity. “Due soon” means within 30 days, including today. Date comparisons use UTC.
- Frame embedding is denied, MIME sniffing disabled, and browser permissions restricted. The CSP restricts framing, objects, and base URLs; it is not a full nonce-based script CSP.

## Verification

```sh
npm run lint
npm run typecheck
npm test
npm run build
```

The validation tests run offline. The database integration test is intentionally skipped unless all three variables below are provided. Use a **dedicated test Supabase project** with the migration already applied. The test creates two disposable confirmed users through the admin API and deletes them in `finally` (cascading their records).

```sh
TEST_SUPABASE_URL=... \
TEST_SUPABASE_PUBLISHABLE_KEY=... \
TEST_SUPABASE_SERVICE_ROLE_KEY=... npm test
```

That suite verifies anonymous table denial, tenant read/write isolation, owner spoofing denial, unauthorized pass creation/revocation, hidden token hashes, exact public field scope, invalid tokens, expired and revoked passes, and the active-pass cap. The test service key must never be added to Vercel or any `NEXT_PUBLIC_*` variable.

Manual acceptance: signup → confirm → household → pet → dashboard → vaccination → share → open anonymously → revoke → reload. Also exercise validation failures, an empty vaccination list, keyboard dialogs, and a narrow mobile viewport. No external project is provisioned or deployment performed by the source code.

Implementation references: [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [Next.js authentication](https://nextjs.org/docs/app/guides/authentication).

## Account settings

Open **Account** in the top bar (including on mobile), or the account area at the bottom of the desktop sidebar. `/account` lets a signed-in user save their full name and optional contact phone, view their sign-in email, change their password, and sign out. The saved name also appears in the desktop account area.

No new SQL migration or environment variables are required. Profile details use the current user's Supabase Auth `user_metadata`; they are display information only and never used for authorization. The share RPC's field allowlist excludes account metadata. Contact phone is not a verified login phone number. Email changes and forgotten-password recovery are outside this change.

Password changes validate the current password by signing in with the server-verified user's email, check that the resulting user ID matches, then call `updateUser` with the new and current passwords. This creates a recent session for Supabase's secure-password-change setting. The form requires a different password of at least 12 characters and matching confirmation. Password values are never returned in action state or logged. See [Supabase password security](https://supabase.com/docs/guides/auth/password-security).

Verification for this addition: profile allowlisting, malformed metadata, phone validation, and password confirmation/length checks are covered by offline tests. Live profile persistence and password changes should be checked with a test account after deployment; no real user's password was changed during implementation.
